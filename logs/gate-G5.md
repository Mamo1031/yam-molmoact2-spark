## 問題と対応
- 2026-10-01 20:20 両腕とも server 停止・畳んだ状態で複数モータの LED が赤点滅（ユーザー報告）。受信専用では読めないので、失能フレーム（FF..FD、トルクなし・エラーを消さない）を 1 回ずつ送って返信の状態コードを読んだ：**左 m4（j4）・左 m6（j6）・右 m6（j6）= 0x3「出力軸校正異常」**、右 m7（グリッパ）= 0xD 通信ロス、他は 0x0 失能（赤常灯）。レジスタ読み（0x7FF/0x33、返信 ID は 0x10+モータ番号）：全モータ sw_ver 同一、**OT_value = 100 ℃**（コイル過熱保護値。これまで未確認だった）、timeout = 8000（400 ms）、xout（出力軸エンコーダ）と p_m（ロータ換算）の差は 0x3 のモータでも 0.002〜0.038 rad で健全なモータ（0.003〜0.033）と差がない。達妙取説 V1.3：3 は校正後の校験で偏差が大きいときに出る、通常は出力軸エンコーダ異常、販売元へ。20:31 にユーザーが follower server を起動したところ初期化が通り、`g5 temps` で 14 モータ全部が正常応答（i2rt の clear→enable で 0x3 は消えた＝一過性）。20:38 に腕の電源を入れ直したら再発：左 m4・左 m6・右 m6 に加え右 m7（グリッパ）も 0x3（前回の右 m7 は 0xD）。**電源投入ごとに出る持続的な自己チェック失敗**。clear→enable で消え、hold の定常誤差（≤ 0.0011 rad）も正常なので運用は可能。i2rt へ報告する（出力軸エンコーダか校正データの問題の疑い）。読み出しスクリプトは Spark の /tmp/claude-led/probe.py（状態）・probe4.py（レジスタ）
- 2026-10-01 硬い物を掴むため、グリッパのガードを無効化（ユーザー依頼）：`tracking_err_max` のグリッパ 0.2 → 1.0、`chunk_first_step_max_gripper` / `chunk_step_max_gripper` 0.5 → 1.0（`configs/dry_run.yaml`）。理由：グリッパが物の幅で止まると方策は「閉」を出し続けるので追従誤差が数 tick で 0.2 を超えて保持に入り、`send(measured)` で把持力まで抜けていた。再計画した chunk の初動も実測（物の幅）から最大 0.9 離れる。把持力の上限は i2rt 側の `limit_gripper_force` 50 N。あわせて `dryrun/executor.py` を変更：(1) 生存監視を関節だけで判定（止まったグリッパ目標だけが動く状況の誤検知を防ぐ。グリッパだけが動く間はモータ監視が頼り）、(2) 異常保持ではグリッパ目標を維持し、Enter だけが全部離す（以前は全 FAULT で `send(measured)` となり物が離れた）、(3) r の戻し動作はグリッパ目標を維持（開くのは o）、(4) 保持中の o/r キーを取りこぼす不具合を修正（1 tick 1 回の poll に）。腕の閾値は変更なし。pytest 70 件。空のグリッパで動作確認するときは 0.2 に戻す。別プロセスの return-to-start / open-grippers は最初の指令が実測なので握った物はその時点で離れる。未確認：物の重さで腕の追従閾値に当たらないか、方策が止まったグリッパの state を見て閉じ続けるか（state をそのまま返すと再計画のたびに力が抜ける）、グリッパモータ（m7）の発熱
- 2026-09-30 18:45 余裕 0 cm でもボール把持の途中で床監視の保持が続いた（方策が机面より下を要求）。ユーザー指示「マイナスは 0 に丸めるだけ、止めない」→ 床監視を**保持ではなくクランプ**に変更：目標の指先高さが机 + 余裕を下回る tick は、高さだけを机面まで持ち上げる最小の関節修正（高さ勾配方向の最小二乗、水平方向の動きは残す）をかけて送る。開始時の高さによる拒否も廃止。クランプした tick 数は `summary.json` の `floor_clamped_ticks` と実行中のログに出る。追従誤差・範囲・モータ監視による保持は従来どおり
